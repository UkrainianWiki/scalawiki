## Context

The oblast-level `Regional statistics` table (`Output.regionalStat`, `MonumentsPicturedByRegion` with `parentRegion == contest.country`) is keyed off `Country.Ukraine.regions`, which is built from `Koatuu.regions()` — the pre-2020-reform KOATUU hierarchy (oblast → old raion → settlement). Monument IDs are geocoded against this same settlement-level KOATUU scheme (`MonumentDB.placeByMonumentId`). `--regional-details` currently recurses exactly one level below oblast (`regionId.length == 2` is the only trigger) into those old-scheme raions, and always renders the full per-year column set.

Ukraine's *current* administrative division (KATOTTH, post-2020) replaces old raions with larger ones and adds a hromada level in between raion and settlement — there is no hromada concept in KOATUU at all. This repo already has a separate, one-off batch tool (`KatotthMonumentListCreator`) that resolves monuments to KATOTTH nodes: it builds a KATOTTH-based `Country` tree via `Katotth.regions()`, and maps each monument's KOATUU settlement code (`placeByMonumentId`, zero-padded to 10 chars) through `Katotth.toKatotth` to a set of candidate KATOTTH nodes, picking the deepest (`maxBy(_.level)`) as the resolved node. Some monuments have no candidate and are reported separately as unmapped. This proposal reuses that same resolution approach inside the live regional-stat report instead of inventing a new one.

See proposal.md for motivation and scope; this document covers only sub-oblast levels (raion, hromada) — the oblast-level table and its per-year columns are unchanged.

## Goals / Non-Goals

**Goals:**
- Resolve each monument to its current-day raion and hromada using the existing KATOTTH data and mapping already proven in `KatotthMonumentListCreator`.
- Render raion and hromada breakdowns as nested tables inside the existing per-oblast wiki page, with no new wiki pages created.
- Keep the nested tables to current cumulative totals (objects in lists, pictured, percentage) only — no per-year history.
- Make recursion depth-agnostic (walk down while there are child regions) instead of the current hardcoded single level, but stop after hromada — do not descend into settlements.
- Surface monuments that can't be resolved to a hromada rather than silently dropping them.

**Non-Goals:**
- No change to the oblast-level `Regional statistics` page or its per-year columns.
- No "changed since last run" delta column or "all-time + 2026" column — deferred to a future change once the 2026 contest starts (per proposal.md).
- No re-resolution of the *oblast* itself via KATOTTH — oblast boundaries didn't change in the 2020 reform, so the existing KOATUU-based oblast identification is left as-is.
- No settlement-level (village/town) breakdown below hromada.

## Decisions

**Use KATOTTH, not KOATUU, for raion/hromada resolution.** The existing one-level "regional details" drill-down reuses `contest.country.regions` (KOATUU-based) for its one extra level. That tree has no hromada level and its raions are pre-reform boundaries, which is exactly the "historical" admin division the request says to avoid. Instead, build a `Katotth.regions()`-based `Country` (mirroring `KatotthMonumentListCreator.UkraineKatotth`) once per report run, and use it only for sub-oblast levels.
- *Alternative considered*: extend `Koatuu.regions()`'s data to add a hromada layer. Rejected — KOATUU has no hromada concept; the data doesn't exist at that granularity, and KATOTTH already models it correctly.

**Resolve hromada primarily from each monument's own list-page title, falling back to the `Katotth.toKatotth` numeric mapping only when the page doesn't resolve.** `KatotthMonumentListCreator` was built in 2021 to *migrate* monument lists onto hromada-organized page titles (its `новий АТУ` draft pages). That migration has since happened for real: live monument list pages (e.g. `Вікіпедія:Вікі любить пам'ятки/Київська область/Білоцерківський район/Ковалівська громада`) already encode oblast/raion/hromada in their titles. Implemented as `KatotthResolver.resolveFromPage` (page parsing + oblast/raion-scoped name matching + seat-type disambiguation), tried before the existing `katotthFor` in `KatotthResolver.resolve`. Verified against the actual cached monument list (`csv-cache/wlm-UA-monuments.csv`, 115,683 monuments, run 2026-09-13):
  - **88.99%** of monuments resolve directly from their page title alone (`resolveFromPage`).
  - Combined with the unchanged numeric fallback for whatever the page title can't place, **93.51%** resolved overall before the KATOTTH data refresh below, rising to **94.02%** (108,765/115,683) after it — leaving **5.98%** (6,918 monuments) unresolved by either method. The remaining gap was dominated by Kyiv/Sevastopol/occupied-Crimea pages, which structurally have no hromada level regardless of codifier edition — addressed by the raion/city-district grouping decision below.
  - After that fix, a naive whole-database tally showed 8 rows still unresolved (a `resolved.size` subtraction, which undercounts whenever multiple rows share a monument id). Listing them individually instead of subtracting counts showed the true picture: those 8 rows never reach the oblast-scoped resolution the live report actually performs at all (see the bad-ids decision below) - once measured per-oblast the way `communityBreakdown` actually runs, **0 monuments with a correctly-prefixed id are geographically unresolved**; every one places at hromada, raion, or district level.
  - A same-raion name collision (e.g. Sumskyi raion has two separate hromadas both named "Миколаївська," one seated in an urban-type settlement, one in a village) is resolved by comparing the page title's disambiguating adjective (міська/сільська/селищна) against the regionType of each candidate hromada's administrative-seat settlement — identified not by naive first-child-in-list-order, but because KATOTTH numbers the seat's own sub-code lowest (conventionally `...010...`), which is what actually makes it sort first; verified directly against the raw `katotth.csv` rows for every real collision found. This generalizes a disambiguation `KatotthMonumentListCreator.main` already anticipated via a small hardcoded set of exactly these KATOTTH codes.
  - **Scoping is capped at oblast level, with no country-wide fallback.** An early version tried an unscoped, name-only match anywhere in the country as a last resort; real-data testing showed this produces false positives more often than correct matches (e.g. a Dnipropetrovsk oblast page named "Самарівська громада" would have wrongly matched an unrelated "Самарівська" hromada that only exists in Volyn oblast — a coincidental name collision, not the right one). Matching now stops at oblast scope and reports unresolved rather than guessing further.

  The numeric `Katotth.toKatotth` path (`KatotthResolver.katotthFor`, already implemented) is kept as the fallback for whatever the page-title parse can't place, rather than removed — it is still useful when a page truly carries no hromada information.
  - *Alternative considered*: numeric-code resolution as primary (the original decision in this document). Superseded — page titles are now the more authoritative, more complete signal, and using them first avoids most of the koatuu-code-mapping's inherent gaps.
  - *Alternative considered*: resolve on the fly per raion/hromada row via repeated lookups. Rejected — same reasoning as before: build one `monumentId -> AdmDivision` map (from whichever signal resolves it) once per report run, not per row.

**Refresh the bundled `katotth.csv` from the current official codifier.** `katotth.csv` was added in a single 2021-06-06 commit and never updated. Ukraine's Ministry for Development of Communities, Territories and Infrastructure publishes dated editions of the КАТОТТГ codifier at [mininfra.gov.ua](https://mininfra.gov.ua/diialnist/rozvytok-mistsevoho-samovriaduvannia/kodyfikator-administratyvno-terytorialnykh-odynyts-ta-terytorii-terytorialnykh-hromad) (also mirrored on [data.gov.ua](https://data.gov.ua/dataset/43c2a113-a032-4c8a-a409-3b5e1660bb38/resource/ee820044-92ff-4a40-b856-71606e2e03f5)), roughly monthly. **Done**: refreshed to the **07.07.2026** edition (sourced and XLSX→CSV converted by the user directly; same 7-column schema as before, so no parsing-code changes were needed). Result: unresolved rate dropped from 6.49% to 5.98% — a smaller gain than hoped, because most of the remaining gap (Kyiv/Sevastopol/occupied Crimea) is structural, not a stale-naming problem the data refresh could fix. `katotth_koatuu.csv` was left as-is: it's a historical KATOTTH↔KOATUU crosswalk fixed at the 2020 reform, not something a later KATOTTH edition's new/renamed hromadas would have an entry in regardless.
  - *Alternative considered*: a hand-maintained alias table mapping known renamed/reorganized hromada names to KATOTTH codes. Not needed — refreshing the underlying data addressed the root cause directly.
  - Refreshing the data also surfaced two real bugs, both caught by tests before they could reach production: the seat-type disambiguation's "селищна" adjective only matched regionType `T`, missing the plain-`X`-type seat the new edition revealed for one collision case (Ukrainian usage doesn't distinguish `T`/`X` in casual page titles); and a hardcoded test expectation for a monument that used to fall through to a false near-miss in an unrelated oblast, since the newer edition now correctly includes a hromada the old snapshot was missing entirely.

**A monument whose page names a raion but no hromada resolves to that raion (or city district), not Unresolved.** Kyiv and Sevastopol structurally have no hromada level at all — their pages name a city district instead (KATOTTH type `B`, район в місті). Occupied Crimea's admin division likewise has no hromada level in KATOTTH. A few mainland raions (e.g. Berehove, Khmelnytskyi) simply haven't had their monument lists split into hromada pages yet. All three cases were previously landing in the oblast-level "Unresolved" bucket for lack of a hromada to match — but the raion (or district) itself is right there in the page title and resolves cleanly. `KatotthResolver.resolveFromPage` now falls back from "no hromada segment" to matching the raion/district segment directly (extending `matchRaion` to accept KATOTTH types `P` and `B`), before falling through further to the numeric mapping. This single change accounted for nearly all of the remaining gap: unresolved dropped from 5.98% (6,918 monuments) to 0 monuments with a correctly-prefixed id (see the bad-ids decision below for the small number of rows that are excluded for an unrelated reason). In the report, these monuments now render as their own raion/district row (nested under the oblast, with an empty hromada breakdown falling to that raion's own "Unresolved" sub-row) instead of one oblast-wide catch-all entry.
  - *Refinement (post-review)*: a raion-only page no longer stops the numeric mapping. `KatotthResolver.resolveDetailed` still takes the page's raion/district, but if `katotthFor` places the monument somewhere *inside that same raion* it uses that deeper location instead. A mapping result outside the page's raion is ignored, since the page title is the more authoritative signal. Without this, a raion not yet split into hromada lists kept every monument at raion level. And once any other monument in that raion reached a hromada, all of them fell into the raion's "Unresolved" sub-row and the "Data issues" list.
  - *Codifier drift (post-review)*: the refreshed `katotth.csv` no longer lists some settlements that the frozen `katotth_koatuu.csv` still points at. 13 were dropped in the 07.07.2026 edition, and 3 were already missing before. One more, Левітанівка, was renumbered, and its mapping row was repointed to the new code. For codes the codifier no longer has, `KatotthResolver.nodeForCode` falls back to the nearest surviving ancestor, the hromada or else the raion, using the code's own hierarchical digits. `KatotthResolverSpec` now checks that every hromada- and settlement-level mapping code resolves, so a future refresh can't silently drop places again.
- *Alternative considered*: leave these as oblast-level Unresolved and treat it as an acceptable structural gap. Rejected on user feedback — the raion/district is known and meaningful; grouping by it is strictly more useful than a blanket "couldn't place it" bucket, and Crimea/Kyiv/Sevastopol together were the overwhelming majority of what "Unresolved" actually contained.

**A monument whose id doesn't genuinely belong to the oblast it landed in is reported as a "Bad IDs" row, not folded into Unresolved.** `MonumentDB.byRegion(oblastCode)` groups by `Monument.getRegionId`, which has a fallback: if a monument's id doesn't start with a real oblast code, it retries against the *second* id segment's leading two digits. This exists for some other, older id convention, but it means a malformed id can coincidentally land in a real but unrelated oblast - found on the real cache: a "99-…" special-nomination id (the Jewish Heritage thematic sub-list, which isn't geographically organized at all) with id `99-230-0001` was silently counted under Запорізька oblast, because its middle segment happens to start with "23" (Zaporizhzhia's real code) - even though the monument is actually in Chernivtsi oblast per its own page title. Per user feedback, this is a data-quality problem, not a geography-resolution gap, and conflating the two hides it. `MonumentsPicturedByRegion.communityBreakdown` now partitions each oblast's candidate monument ids into those whose id *literally* starts with that oblast's own code (processed normally) and those that only got there via the fallback (reported as a "Bad IDs" row instead, via a `badIds` parameter on `RegionalCommunityBreakdown.render`). Verified against the real cache: **5 monuments** were previously silently miscounted this way (3 in Запорізька, 1 in Чернівецька, 1 unrelated one - `98-321-0901` - in Київська); none remain miscounted after the fix.
- *Alternative considered*: rely on `MonumentDB.isIdCorrect`/`wrongIdMonuments` to detect these. Rejected - `isIdCorrect` uses the same `getRegionId` fallback internally, so it considers these ids "correct" (the fallback found *some* valid-looking oblast); it doesn't catch this class of misattribution at all. The literal-prefix check in `communityBreakdown` is a distinct, stricter test scoped to this report, not a change to `MonumentDB`'s general id validation (which is out of scope and used elsewhere).
- Two further ids (`99-205-0001`, `99-999-9999`) have no valid-looking oblast prefix under *either* the direct or fallback check, so they never reach any oblast's candidate set at all - neither counted nor flagged, in this report or before it. That's a pre-existing `Monument.getRegionId` limitation, unrelated to and out of scope for this change.

**Unresolved monuments get a per-oblast "Unresolved" row**, per the confirmed answer: still counted in the oblast-level total (unchanged, existing behavior), but broken out as an explicit final row in that oblast's nested raion/hromada table rather than silently vanishing or padding one specific raion's count. This now covers only genuinely unplaceable monuments - measured at 0 on the real cache once bad ids are excluded and raion/district-only areas are handled - not areas that simply lack a hromada level, and not monuments whose id doesn't belong to the oblast in the first place.

**Bad-id detection also checks the *resolved* division's own oblast, not just the id's literal prefix.** Manual review of a real generated page (`Monuments pictured by region in Київ`, i.e. Kyiv *city*) found a `Бучанський район` section - a Kyiv *oblast* raion - nested inside Kyiv city's own report. Cause: a handful of WWII fortification-point monuments have ids starting with "80" (Kyiv city's numeric prefix, so they pass the existing id-prefix bad-id check for Kyiv city) but are listed on a Kyiv-oblast hromada's page, which is what `resolveFromPage` actually uses. Since KATOTTH codes carry their oblast's 2-digit prefix at every level (verified against the raw `katotth.csv` rows), comparing `katotthResolution(id).code.take(2)` against `parentRegion.code` catches this directly: `communityBreakdown` now runs both checks (id-prefix, then resolved-division-prefix) before accepting a monument as genuinely of this oblast, moving either kind of mismatch into `badIds`. An unresolved id (no `katotthResolution` entry) is left alone by this second check - it still lands in the ordinary oblast-level Unresolved row, since "we don't know where it goes" is a different situation from "we know, and it's not here." Verified against the real cache: nationwide, this brought the Bad IDs count from 5 (caught by the id-prefix check alone) to 12.
- *Alternative considered*: only run the id-prefix check (the original bad-ids decision above). Rejected once real data showed it insufficient - an id can honestly start with the right oblast's digits and still be listed under a different oblast's page.

**A monument list page split across several sub-pages links to the first one - but only among pages that actually name the region, not just whichever sorts first overall.** Manual review of `Monuments pictured by region in Чернівецька область` found several hromada rows and raion headings linking to the "Єврейська спадщина" (Jewish Heritage) thematic page - unrelated to geography - instead of their own real list page. Cause: some of a hromada's monuments are only resolved into it via the numeric fallback from that thematic page (a monument can genuinely belong to a hromada while being catalogued by theme rather than geography on-wiki), and "Єврейська спадщина" happens to sort alphabetically before most oblast names, so the original "sort all candidate pages, take the first" logic picked it every time it was among the candidates. `linkedName` now first restricts candidates to pages that `KatotthResolver.parsePage` actually parses as naming this region (its hromada or raion stem matching the row's own name); only when *no* candidate page names the region does it fall back to the original "all candidates, alphabetically first" behavior, which is what correctly handles the legitimate split-page case. Verified against the real cache: 0 remaining links to the thematic page, down from 5.
- *Alternative considered*: exclude known thematic/special-nomination pages by pattern (e.g. hardcode "Єврейська спадщина"). Rejected - fragile against future thematic sub-lists and doesn't address the general principle; checking that a candidate page actually names the region works for any such case without needing to enumerate them.

**Linking uses `KatotthResolver.resolveDetailed`'s `pageById`, not a separate `MonumentDB.byId` lookup.** A handful of WLM ids are duplicated by data-entry error across two different monument list pages (real case: id `85-369-0198` appears once each in Sevastopol's Нахімовський and Балаклавський district lists). `MonumentDB.byId`'s `_byId.headOption` (first-encountered wins) and `KatotthResolver.resolve`'s `.toMap` construction (last-encountered wins) collapse such a duplicate independently and can therefore disagree about which of the two "wins" - which previously meant a raion's link could point at a *different* raion's page than the one its own count was built from. `KatotthResolver.resolveDetailed` returns each id's resolved division *paired with* the page that produced it, both from the same winning `Monument` in one pass, so they can never disagree; `MonumentsPicturedByRegion` threads this through as `pageById` and `RegionalCommunityBreakdown.linkedName` reads from it instead of touching `MonumentDB` at all. Verified with a unit test reproducing the exact duplicate-id shape, and an end-to-end test asserting neither Sevastopol district ever links to the other's page regardless of which side of the duplicate wins.
- *Alternative considered*: keep using `MonumentDB.byId` and special-case known duplicate ids. Rejected - fixes the one instance found, not the class of problem, and doesn't help if another duplicate id is introduced later.

**Recursion terminates at hromada (KATOTTH `regionType.code == "H"`), not by depth-counting.** Replace the current `regionId.length == 2` check with "recurse into `regions` while the current node's `regionType` is oblast or raion" so the walk is driven by what the hierarchy actually contains rather than a magic code length, but still stops one level below hromada (no settlements).

**Nested tables are built and returned as wikitext, not written as separate pages.** The current recursive design has each level call `.updateWiki(bot)` on itself, i.e., every level performs its own page write. For raion/hromada, refactor so the sub-oblast levels build wikitext bottom-up (hromada rows → raion section containing them → returned to the oblast page) and only the oblast-level page write persists to Commons. This keeps the change additive to `MonumentsPicturedByRegion` rather than restructuring the oblast-level write path, which stays exactly as it is today.
- *Alternative considered*: keep per-level `.updateWiki` calls but point them all at the same oblast page name so later writes overwrite earlier ones with accumulated content. Rejected — fragile (relies on edit ordering) and would still cost redundant HTTP round-trips for no benefit over building the text in memory first.

**Totals-only rendering is a separate code path from the existing per-year `Table` construction**, not a flag threaded through `columns`/`monumentsPicturedTable`. Those methods assume the year-oriented column list is the shape of every row. Building a minimal three-column (name, in-list, pictured, %) table for raion/hromada rows directly is simpler than parameterizing the existing per-year machinery to sometimes omit most of its own columns.

**Raion and hromada names link to their monument list page, derived from the monuments' own `page` field rather than a naming convention.** Per user feedback: since we already know exactly which monuments belong to each row, the simplest and most reliable way to find "that region's list page" is to look at the `page` value the monuments themselves carry (from the live wiki list), not to construct a URL from the region's name. `RegionalCommunityBreakdown.linkedName` collects the distinct pages among a row's monuments and links to the alphabetically first one. This naturally handles both cases: a region on one page links directly to it; a region whose list is split across several alphabetic sub-pages (e.g. "Львівська громада (А–В)", "(Г)", ...) links to the first, which — per the user — carries a navbar to reach the rest, so no page-enumeration logic is needed here. Applied to hromada row names and to the raion name used as each section's heading; not applied to the "Unresolved," "Bad IDs," or "Total" labels, since those don't denote one place.
- *Alternative considered*: construct the expected page title from the region's name and hierarchy (mirroring `KatotthMonumentListCreator`'s page-naming logic). Rejected — reading the real `page` field already on hand is simpler and immune to page-naming-convention drift; it is by definition always correct for whatever pages actually exist.

**Each raion's hromada table gets a Total row, and the oblast breakdown gets a final overall Total section.** Per user feedback. The raion-level Total is computed the same way as any other row — `totals()` over that raion's full monument id set — rather than summing the other rows' formatted strings, so it can't drift out of sync with them. The oblast-level Total is a new final section mirroring the same pattern, summing `oblastMonumentIds` (which already excludes bad ids).
- *Follow-up per user feedback*: for a multi-table oblast, a lone grand-total row in that final section throws away the at-a-glance per-raion comparison the individual raion sections already gave. The Total section now lists every raion's own total row first (split and shared/unsplit raions alike, sorted by name and `linkedName`-linked like their own section/row), then the oblast-level Unresolved row if any, then the grand total - one table that both compares raions and summarizes the oblast, rather than a section that only did the latter. Verified against the real cache for Львівська oblast: its 7 raion totals (378/525/3622/381/682/477/255) now appear before the grand total (6320).

**A raion with no hromada breakdown at all gets one row in a shared "Raions" table, not its own nested section.** Caught by user feedback on the actual Crimea output: a raion with zero hromada rows (Crimea has no hromada level at all; a handful of mainland raions aren't split yet either) produced a nested table whose only two rows - "Unresolved" and "Total" - were always identical, since the raion's entire monument set *is* its own Unresolved bucket. `RegionalCommunityBreakdown.hasHromadaBreakdown` partitions each oblast's raions into those with at least one hromada row (rendered as before, via `renderRaion`) and those with none (collected into one shared table titled "Raions", one linked row per raion, no separate section or redundant Unresolved/Total pair). For Crimea specifically, every raion falls into this second group, so the whole oblast now renders as a single clean raions table instead of ten near-empty two-row tables.
- *Alternative considered*: keep the per-raion nested table but drop its "Unresolved" row when it would duplicate the "Total" row. Rejected — still leaves a pointless one-row table with a redundant `Table` wrapper (headers, caption) around a single number; folding all such raions into one shared table is more compact and reads better for exactly the case (all of Crimea) where it dominates the oblast's output.

**Every problematic monument (bad id, wrong region, unresolved, duplicated id) is itemized in one explained "Data issues" list, replacing the separate count-only "Bad IDs" section, the plain unexplained "Wrong region ids" section, and the raw duplicate-id ambiguity that caused the two link bugs above.** Per user feedback: knowing "3 monuments are bad ids" or seeing a bare comma-separated id list doesn't tell an editor what to actually fix; each entry needed to say *why*. `RegionalCommunityBreakdown.Issue(id, name, category, explanation)` covers four categories: **Bad id** (id doesn't start with this oblast's code), **Wrong region** (id does, but the page resolves elsewhere - explanation names the resolved oblast/raion/hromada via the resolved division's own ancestor chain), **Unresolved** (no raion/hromada/district found at all, or only down to raion level - both are surfaced, in addition to the existing numeric "Unresolved" row/section, which is kept for a quick per-raion/oblast count), and **Duplicated id** (`duplicateIdIssues` finds every id shared by more than one monument in `MonumentDB.allMonuments` and lists every page it appears on). An id already flagged as duplicated is excluded from the other three categories, since "which of the two colliding monuments is 'wrong' " isn't a meaningful question - the id collision itself is the issue to fix. `MonumentsPicturedByRegion.asText` also stops appending the old (pre-2020-KOATUU-based) `wrongRegionIds` output for the oblast subpage specifically (it's kept, unchanged, for the top-level oblast table, which is out of scope for this change) - the new list is its replacement there. Verified against the real cache: Kyiv's list surfaces its 4 "Wrong region" fortification points plus 10 legitimate same-monument cross-page listings correctly labeled "Duplicated id" (e.g. the Baikove Cemetery memorial complex, listed on both the district's alphabetic page and its own thematic sub-page); Chernivtsi's list surfaces the 7 monuments that were the actual root cause of the earlier "links to Єврейська спадщина" bug, each now correctly labeled "Duplicated id" (same monument, listed on both its real hromada page and the thematic special-nomination page) rather than causing a bad link.
- *Alternative considered*: keep "Bad IDs" as a count and add a separate new itemized section only for the newly-discovered duplicate-id case. Rejected on user feedback - a single, consistent, explained list for every category is more useful than a count for some and an itemized list for others.
- *Alternative considered*: look up each duplicated id's monument name via `MonumentDB.byId` (single, arbitrary pick) like the other categories do. Rejected specifically for duplicates - the whole point of this entry is that more than one monument shares the id, so the explanation lists every one of them (name and page), not just whichever `byId` happens to return.

**The Chornobyl Exclusion Zone gets a hardcoded special case, not a general rule.** `Вікіпедія:Вікі любить пам'ятки/Київська область/Вишгородський район/ЧЗВ` names no hromada (per `parsePage`, "ЧЗВ" doesn't end in "громада"), so it would otherwise resolve only to Вишгородський raion and land in that raion's "resolved to raion but not to a hromada" Unresolved bucket - technically correct, but ЧЗВ (Чорнобильська зона відчуження) is a real, well-known area distinct from any hromada, not a data gap. Per user request, `KatotthResolver.resolveFromPage` checks for this one exact page before the general parsing logic and returns a synthetic hromada-level (`regionType` "H") `AdmDivision` named "Зона відчуження ЧАЕС", parented to the real Вишгородський raion node - so it flows through every existing mechanism (grouping, linking, `hromadaAncestor`/`raionAncestor`) exactly like a real hromada, with no special-casing needed anywhere else.
- *Alternative considered*: generalize this into a rule (e.g. "a raion-only page with a distinctive name gets its own group"). Rejected - there is exactly one such case in the current data, and inventing a general rule for it risks matching something unintended later; a hardcoded page-and-name pair is simpler, obviously scoped, and trivial to extend if another such case turns up.

**When an oblast's breakdown produces exactly one table overall, the Total row is merged into it instead of appended as a separate table.** Found via user review of Kyiv city's actual output (Raions-table-only, since none of its districts split further): a separate "==== Total ====" section right after the one existing table just repeated the same numbers in a second table. A lone split raion's own table, or the oblast-level Unresolved table, already ends with a row that *is* the oblast total (nothing to add); only the "Raions" table has no such row of its own, so it gets the Total row appended directly rather than a second table.

**"Duplicated id" page mentions and monument-name wikilinks are rewritten to the `:uk:` interwiki prefix, and the "Wrong region" explanation links its named location.** Per user review of real output: plain page names in the duplicate-id explanation weren't clickable, and a monument name's own embedded `[[wikilink]]` (targeting a ukwiki article, since names come from ukwiki lists) rendered as a broken same-titled Commons link on this Commons-hosted page - the same class of problem `Output.scala` already solves elsewhere with `.replaceAll("\\[\\[", "[[:uk:")`, now applied here too via `wikifyName`/`wikifyPage`. The "Wrong region" explanation's location is now a link to the monument's own page (via `pageById`) rather than plain text naming the oblast/raion/hromada chain.

**The "Bad id" and "Wrong region" explanations were reworded for clarity.** Per user feedback that "this id starts with this oblast's own code" didn't actually say what was *wrong* - it stated a fact about the id without connecting it to the problem. Both now lead with the actual issue ("this monument's id does not start with this oblast's own numeric code, so it doesn't genuinely belong here"; "this monument's id looks like it belongs to this oblast, but its own list page actually places it in ...").

## Risks / Trade-offs

- **Resolution gaps**: not every monument will resolve to a hromada (as already observed by `KatotthMonumentListCreator`'s unmapped-monument reporting) → mitigated by the agreed "Unresolved" row per oblast, so gaps are visible rather than hidden, and organizers can act on `Output.unknownPlaces`-style follow-up if the unresolved count is large.
- **Report run time**: resolving every monument through `Katotth.toKatotth` and building nested tables for ~136 raions and ~1,470 hromadas adds CPU work to each `--regional-details` run → mitigated by computing the monument→KATOTTH map once per run (not per row) and reusing the existing `MonumentDB`/`ImageDB` indexes for counting.
- **KATOTTH data drift**: hromada boundaries and names can change (further reform, renames like Zvyahel, front-line-oblast reorganization) and the ministry republishes the codifier roughly monthly, so today's refreshed `katotth.csv` will itself go stale again → mitigated for this change by refreshing to the current (07.07.2026) edition and keeping the numeric fallback for whatever a future rename breaks; a recurring refresh process (e.g. checked each contest season) is a reasonable follow-up but not built here.

## Open Questions

None — the two decisions that would have changed spec-level behavior (nested-table shape and unresolved-monument handling) were resolved with the user before writing this document.
